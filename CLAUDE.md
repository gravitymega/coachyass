# Coachyass / Gravity Basketball — contexte projet

Ce repo (`gravitymega/coachyass`) héberge plusieurs sites statiques déployés séparément sur Netlify, tous sous le domaine `osmm-mtl.site` (sauf le Dashboard). Chaque site = un sous-dossier avec son propre `netlify.toml` (`publish = "."`).

Les templates `courriel-confirmation.html` et `courriel-notification-admin.html` ont été supprimés (plus utilisés). Fonctionnalité "Forms" activée côté API sur le site `talent-perle`.

Compromis assumé (choisi explicitement par l'utilisateur après lui avoir présenté l'alternative) : **il n'y a plus de confirmation automatique envoyée au parent** — Karim reçoit seulement la notification de Netlify et doit répondre lui-même au parent pour confirmer. C'est le même compromis qu'un essai de simplification EmailJS du 4 septembre qui avait été annulé sur le moment — cette fois-ci le choix est délibéré (fait pour simplifier l'infrastructure, pas juste le flux de courriel), donc ne pas revenir en arrière sans redemander confirmation.

**14 septembre 2026 : copie optionnelle des inscriptions dans un Google Sheet du Drive de Karim.** En plus de Netlify Forms (qui reste la source de vérité + la notification courriel), le formulaire peut aussi envoyer chaque inscription dans un Google Sheet, via un petit script Google Apps Script (`talent-perle-site/google-apps-script-inscriptions.gs`, à coller une fois par Karim dans un Sheet de son Drive puis déployer comme application web). Choisi plutôt que Zapier pour rester sans compte tiers, cohérent avec le choix Netlify Forms du 12 septembre.

**Les inscriptions elles-mêmes restent sans dashboard** : contrairement aux autres sites, il n'y a pas de backend (Notion/Supabase) derrière les *inscriptions*. Ce choix (pas un manque) reste inchangé — voir la section "Dashboard Talent Perlé" ci-dessous pour ce qui, en revanche, est maintenant géré par un vrai backend (activités, photos, événements, partenaires — pas les inscriptions).

**Architecture :**
- `talent-perle-dashboard/schema.sql` : à exécuter une seule fois dans le nouveau projet Supabase (SQL Editor). Crée 4 tables (`activities`, `photos`, `events`, `partners`), active la RLS avec lecture publique seule (écriture réservée à la clé `service_role`, jamais exposée au client), crée le bucket de stockage public `talent-perle`, et pré-remplit `activities` avec les 5 activités actuelles du site (Soccer, Volleyball, Tennis, Basketball, **Jeu d'échecs** — remplace "Activités culturelles").
- `talent-perle-dashboard/netlify/functions/admin.js` : unique fonction serveur, porte d'entrée pour toutes les opérations (list/create/update/delete/upload). Vérifie l'en-tête `x-admin-password` contre `DASHBOARD_PASSWORD` (variable d'environnement Netlify) à chaque appel, puis parle à Supabase avec la clé `service_role` (également en variable d'environnement : `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`).
- `talent-perle-dashboard/index.html` : page d'accès (mot de passe) + 4 onglets (Activités, Photos, Événements, Partenaires), chacun avec un formulaire d'ajout (upload d'image direct vers Supabase Storage via la fonction) et une liste avec suppression/masquage.
- `talent-perle-site/index.html` : lit maintenant Supabase en lecture seule (clé `anon`, publique par design) pour peupler dynamiquement la grille d'activités **et** le menu déroulant du formulaire d'inscription (une seule source de données pour les deux — toute activité ajoutée par Karim apparaît automatiquement dans le formulaire), ainsi que Galerie/Calendrier/Partenaires. Config dans la variable `TP_SUPABASE` (bloc `<script>` dédié, juste après `TP_SHEET_URL`) — **vide par défaut**, le site utilise alors un tableau JS `FALLBACK_ACTIVITIES` statique (les 5 mêmes activités) et les sections Galerie/Calendrier/Partenaires gardent leur contenu d'exemple statique, donc aucune régression tant que Supabase n'est pas branché.

**Reste à faire côté utilisateur/Karim pour activer le dashboard :**
1. Créer un compte Supabase (gratuit) séparé de l'écosystème Gravity, créer un nouveau projet.
2. Exécuter `talent-perle-dashboard/schema.sql` dans son SQL Editor.
3. Créer un site Netlify pour `talent-perle-dashboard/` (base directory = `talent-perle-dashboard`, publish = `.`), comme pour `talent-perle-site/`.
4. Sur ce nouveau site Netlify, ajouter les variables d'environnement `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` (Project Settings → API → `service_role`, secret) et `DASHBOARD_PASSWORD` (mot de passe au choix pour Karim).
5. Sur `talent-perle-site/index.html`, remplir `TP_SUPABASE.url` et `TP_SUPABASE.anonKey` (Project Settings → API → `anon` `public`, celle-là est sans danger à exposer côté client).
6. Si l'URL du dashboard n'est pas `talent-perle-dashboard.netlify.app` une fois le site créé, mettre à jour le lien "Accès administrateur" dans `talent-perle-site/index.html` (section Espace membre).

## Art craft (19 octobre 2026)

Projet de l'utilisateur : « Art craft », une future application de montage vidéo / studio son / studio image, **pour Gravity au départ**. Construite par étapes ; la V1 est le **Highlight Agent** (`art-craft/`) : on dépose la vidéo d'une game entière, l'agent repère les temps forts et sort un highlight vertical (9:16) de **20 s à 3 min** (menu « Durée du highlight » : 20 s, 30 s, 45 s, 1 min par défaut, 1 min 30, 2 min, 2 min 30, 3 min ; élargi le 19 octobre 2026 à la demande de l'utilisateur). Jusqu'à 80 moments forts sont repérés au son, et le nombre vérifié au filet grandit avec la durée visée (`checkedFor`, de 30 à 80).

- **100 % dans le navigateur**, aucun serveur ni clé API : moteur **ffmpeg.wasm** (open source). L'enveloppe (`vendor/ffmpeg/ffmpeg.js` + `814.ffmpeg.js`, @ffmpeg/ffmpeg 0.12.10, licence MIT) est servie par le site, parce qu'un Worker doit venir de la même origine. Le cœur (`@ffmpeg/core@0.12.6`, 32 Mo) est chargé depuis unpkg en blob URL. La vidéo est montée en **WORKERFS** (lue morceau par morceau, jamais copiée en mémoire), donc une game de plusieurs Go passe.
- **Détection** (`art-craft/highlights.js`, module pur testable avec Node) : extraction du son en mono 8 kHz → niveau en dB par fenêtre de 0,25 s → score = niveau lissé sur ~1 s moins l'ambiance locale sur ~40 s (réaction de la salle). Les pics sont espacés d'au moins 12 s. Chaque extrait va de 6 s avant à 2 s après le pic (l'action précède la réaction). Les meilleurs pics sont présélectionnés jusqu'à la durée visée.
- **Ajustements dans l'interface** : graphique d'excitation cliquable, cocher/décocher, ±1 s, durée par extrait, ajout manuel (moment affiché dans la vidéo, ou liste de minutes `3:12, 15:40`), aperçu enchaîné.
- **Habillage** : plein cadre + fond flou (par défaut) ou recadré (curseur de cadrage par extrait), 1080×1920 ou 720×1280. Titre, score et logo sont dessinés en PNG sur un canvas, puis superposés. Le rendu se fait en un seul encodage ffmpeg (libx264 ultrafast + AAC), avec un téléchargement MP4 et un bouton Partager (Web Share API, mobile).
- **Paniers marqués + zoom (19 octobre 2026, demande « focus sur les ballons marqués » et « zoomer les actions »)** :
  - Le son seul ne distingue pas un panier d'un contre. L'utilisateur touche le **cercle du panier** (1 ou 2 paniers) sur une image de la game extraite par ffmpeg (bouton « Autre image », curseur « Taille de la zone »). Pour les 30 moments forts les plus forts au son, `netMotionArgs` extrait la zone cercle + filet (`hoopBox`, coordonnées 0 à 1, donc indépendantes de la résolution et de la rotation) en 16×16 gris à 15 i/s, sur les 8 s précédant la réaction. `netMotion` + `basketPeak` mesurent le pic de mouvement (z robuste médiane/MAD). Au-dessus de `BASKET_Z` = 6, c'est un panier, et son heure exacte `tb` sert d'ancre à l'extrait (5,5 s avant, 2 s après). Le menu « Garder » choisit entre « les paniers marqués » (par défaut quand au moins un panier est trouvé) et « tous les moments forts » (`candidatesToClips`).
  - **Limite** : il faut une caméra **fixe**. Un joueur qui touche le filet sans marquer peut aussi déclencher. Seuil calibré seulement sur une game synthétique (paniers z≈84, faux cri z≈1) : à valider sur une vraie game.
  - **Zoom** (menu « Zoom sur l'action » : aucun / léger 1,4 / fort 1,8 par défaut / très fort 2,3) : filtre `zoompan` par extrait (`zoomFilter`, taille de travail `zoomSize` ≤ 1280 px, lue dans le journal ffmpeg avec la rotation des téléphones). Sur un panier, le zoom progresse vers le filet entre `tb`−2,2 s et `tb`−0,3 s (lissage smoothstep), puis reste serré. Sur un autre moment, zoom avant doux au centre. En mode recadré, le cadrage d'un panier se place par défaut sur le panier.
- **Games de 2 h (20 octobre 2026)** : le son est extrait par tranches de 10 min (`AUDIO_CHUNK_S` dans `app.js`, `-ss`/`-t` à chaque tranche), l'enveloppe est calculée tranche par tranche puis recollée : la mémoire reste la même quelle que soit la durée (important sur téléphone). Testé dans Chromium avec une fausse game de 2 h de 5,5 Go (720p, 6 Mb/s) : analyse en 4 min, short de 27 s rendu en 50 s. Une game de 2 h de 760 Mo s'analyse en 51 s.
- **Publier sur Instagram et Facebook (20 octobre 2026, demande « lorsque le highlight est fini, l'envoyer directement sur Instagram ou Facebook avec titre et hashtags »)** : panneau « Publier » sous le short (`social.js` + `social-core.js`, pur). Légende = titre · sous-titre de l'habillage + texte libre + hashtags (8 proposés par défaut, `DEFAULT_TAGS`, dédoublonnés, 30 max, 2 200 caractères max), modifiable avant envoi. Cases Instagram (reel) / Page Facebook, confirmation obligatoire. **Réutilise la passerelle Meta du Dashboard** (`gravity-admin-dashboard/netlify/functions/instagram.js`, jeton `META_PAGE_ACCESS_TOKEN` côté serveur, aucun secret dans Art craft) : connexion avec le **compte admin du Dashboard** (Supabase Auth en REST, session gardée dans le navigateur), dépôt de la vidéo dans le bucket public `gravity-media/instagram/art-craft-….mp4` (limite 100 Mo), puis reel Instagram (`create_container` → `container_status` → `publish_container`) et vidéo de Page Facebook (nouvelles actions `facebook_video` via `graph-video.facebook.com/me/videos` avec `file_url`, et `facebook_video_status`), en parallèle, avec un lien vers chaque publication. Le débit du rendu est plafonné (`uploadKbps` → `maxKbps` de `buildRenderArgs` : 8 Mb/s en 1080p, 5 Mb/s en 720p, moins pour les longs shorts) pour rester sous ~90 Mo. Sans connexion, « Partager… » (mobile) copie la légende et ouvre Instagram/Facebook. **Ne marche qu'une fois `META_PAGE_ACCESS_TOKEN` ajouté** sur `gravity-admin-dashboard` (voir « Intégration API Meta / Instagram » : il faut aussi la permission **`pages_manage_posts`** dans le jeton pour Facebook). Testé avec Meta et Supabase simulés (mauvais mot de passe refusé, envoi, reel + vidéo Facebook publiés, liens affichés).
- **Enregistrer dans Google Drive (20 octobre 2026, demande « stocker mes shorts dans Google Drive après traitement »)** : bloc « ☁️ Enregistrer dans Google Drive » sous le short (`drive.js`). Connexion Google officielle (Google Identity Services, `accounts.google.com/gsi/client`) avec la seule permission `drive.file` (l'outil ne voit que les fichiers qu'il crée), dossier « Art craft — Gravity » créé au besoin, envoi « reprenable » de l'API Drive v3 directement depuis le navigateur (progression, lien « ouvrir » à la fin), légende de publication en description. Case « Enregistrer automatiquement les prochains shorts » (mémorisée dans le navigateur) : l'envoi part seul tant que l'accord Google de la visite est valide (la toute première connexion exige un clic). **À configurer une fois** : créer un identifiant client OAuth « Application Web » dans la console Google Cloud (API Google Drive activée, écran de consentement, origine JavaScript autorisée `https://art-craft-gravity.netlify.app`), puis mettre cet identifiant (public, pas un secret) dans `GOOGLE_CLIENT_ID` en haut de `art-craft/drive.js`. Tant qu'il est vide, le bloc affiche un message explicatif. Testé avec Google simulé (dossier créé puis réutilisé, envoi de 9 Mo, envoi automatique du short suivant sans nouvelle connexion).
- **Analyse tactique (21 octobre 2026, demande « analyser les tactiques et le jeu depuis mes vidéos, avec texte et voix » ; choix de l'utilisateur : un outil dans Art craft, résultat = vidéo commentée + rapport écrit)** : module `analyse.html` + `analyse.js` + `analyse-core.js` (pur, testable avec Node) + fonction **`netlify/functions/coach.mts`** (fonction moderne, réponse en flux NDJSON pour rester sous la limite de 60 s). Le navigateur choisit une séquence (début + 30 s à 10 min), en tire jusqu'à 32 images JPEG de 640 px (`sampleTimes`, `frameArgs`), les envoie à **Claude** (`claude-opus-5-5`, effort `low`, sorties structurées `ANALYSIS_SCHEMA` : résumé, attaque, défense, transitions, systèmes, points forts/à travailler, conseils, moments clés avec instant, commentaire de voix off d'environ 2,3 mots/s, 60 à 450 mots ; `fallbacks: "default"` activé en cas de refus). Rapport affiché, copiable, téléchargeable en .txt et imprimable en PDF ; moments clés cliquables. Vidéo commentée (`buildCommentaryArgs`) : séquence en 1280×720 ou 1920×1080 (prolongée sur la dernière image si la voix est plus longue), encadrés des moments clés dessinés en PNG aux couleurs Gravity, voix off gratuite Piper générée dans le navigateur (ElevenLabs à l'origine, retiré le 21 octobre 2026) par-dessus le son de la salle baissé à 20 % ; voix off aussi téléchargeable seule en WAV. Dépendance `@anthropic-ai/sdk` déclarée dans `art-craft/package.json` (Netlify l'installe au déploiement ; `node_modules/` ignoré par Git). **Variable Netlify à ajouter sur `art-craft-gravity` : `ANTHROPIC_API_KEY`** (console.anthropic.com → API Keys ; quelques cents par analyse). Limites : l'IA voit des images fixes, pas le mouvement continu (elle déduit en comparant les images). Testé avec l'IA et ElevenLabs simulés (10 images envoyées pour 30 s, rapport, vidéo commentée 1280×720 de 30 s avec encadrés) et la fonction contre une fausse API Anthropic (mot de passe, clé manquante, refus, clé refusée).
- **Analyse tactique v2 : ralenti + tableau du coach (21 octobre 2026, demande de l'utilisateur avec une capture de référence d'un compte Instagram de tactique)**. Trois problèmes signalés : le commentaire allait plus vite que les actions, il manquait un choix pour le son de la vidéo d'origine, et il fallait le format « vidéo en haut, tableau du coach en bas » avec des explications coordonnées aux pions.
  - **Vidéo commentée verticale** : 720×1280 ou 1080×1920. La vidéo (16:9) est en haut, et le **tableau du coach** est en bas (`board.js`, dessin canvas ; `board-core.js`, pur). Le tableau est un demi-terrain FIBA bordeaux, panier en haut. Il montre des pions noirs **PG, SG, SF, PF, C**, les défenseurs en croix, et les trajets : coupe (flèche), dribble (zigzag), écran (barre en T), passe (pointillés). Le ballon est orange. Au-dessus du terrain : n° de l'action, instant, pastille « RALENTI × 0,5 » / « IMAGE FIGÉE », titre et explication.
  - **Ralenti synchronisé avec la voix** (`buildBeats` dans `analyse-core.js`) : la séquence est découpée en passages : intro, chaque action au ralenti (de `debut` à `fin`), le jeu entre les actions à vitesse normale, puis la conclusion. Chaque phrase du coach est synthétisée à part (`synthFree` de `piper.js`, PCM). Si une phrase dure plus longtemps que l'action ralentie, l'action est encore ralentie (jusqu'à × 0,25), puis la dernière image est figée (`tpad`) : **la voix n'est jamais en avance sur le jeu**. Avec « Aucun ralenti », l'image se fige au lieu de ralentir. La piste de voix complète est assemblée dans le navigateur (`placeVoice`).
  - **Pions coordonnés** : pendant chaque action, les pions se déplacent sur leurs trajets et le ballon suit les passes (`boardAt`). Le tableau est rendu en JPEG à 10 images/s pendant les actions, et une seule image pour les passages fixes (`boardFrames`). L'ensemble passe à ffmpeg par une liste ffconcat (`concatList`), puis `vstack` sous la vidéo (`buildTacticArgs` : une entrée `-ss`/`-t` par passage, `setpts`, `fps=30`, `tpad`, `atempo` enchaînés, `concat`).
  - **Choix du son** (menu « Son de la vidéo ») : voix off du coach + ambiance du match à 20 % (par défaut), voix off seule, ou **son original de la vidéo** (sans voix off ; le son ralenti garde sa hauteur grâce à `atempo`). Menu « Ralenti des actions » : aucun, × 0,75, × 0,5 (défaut), × 0,35, × 0,25.
  - **IA en entraîneur expert** (`coach.mts`, nouveau `ANALYSIS_SCHEMA`) : en plus du rapport, `intro` et `conclusion`, et pour 3 à 6 `moments` : `debut`/`fin` de l'action, `narration` (15 à 40 mots, qui nomme les joueurs exactement par leur poste comme sur le tableau), `ballon`, `joueurs` (5 positions x/y), `defenseurs`, et `trajets` dans l'ordre. Le repère est expliqué dans la consigne (x 0 → 1 de gauche à droite, y 0 = ligne de fond → 1 = ligne médiane, panier en (0,5 ; 0,11), points repères). `max_tokens` passe à 16 000. Les positions sont celles que l'IA déduit des images : c'est un schéma de coach, pas un suivi exact des joueurs.
  - **Script modifiable** : une zone de texte pour l'intro, une par action et une pour la conclusion.
  - Testé dans Chromium (IA simulée, voix Piper réelle servie en local), sur une séquence de 30 s avec 2 actions :
    - voix off + ambiance, × 0,5, 720p : vidéo de 41 s ;
    - son original, × 0,25, 1080p : vidéo de 60 s, sans voix off ;
    - voix seule, sans ralenti : vidéo de 34 s, avec images figées.

## Bug découvert : gravity-mailer (Resend) ne livre qu'à un seul destinataire (13 septembre 2026)

**Symptôme** : l'utilisateur ne recevait jamais la notification admin Gravity Prep (`type: 'basketball-mtl-prep-admin'`, envoyée à `Gavitybasketball@gmail.com`), alors que le code existait déjà (PR #32).

**Cause confirmée par test direct** (`curl` sur la fonction en production) : `gravity-mailer` n'a pas de variable `MAILER_FROM_EMAIL` configurée, donc `send-confirmation.js` envoie depuis le domaine de test Resend `onboarding@resend.dev`. **Resend restreint ce domaine à un seul destinataire : l'adresse du compte Resend lui-même** (`moqtad6@gmail.com`) — tout envoi vers une autre adresse échoue silencieusement (502, jamais vu par le visiteur grâce au `.catch(() => {})`). Confirmé par test comparatif : envoi vers `moqtad6@gmail.com` → succès ; envoi vers `Gavitybasketball@gmail.com` → échec.

**Portée réelle du bug** : ça ne touche pas que la notification Prep — **toutes les confirmations clients envoyées par `gravity-mailer`** (Coaching, Pickup, Basketball, OSMM), qui vont vers l'adresse du visiteur, échouent probablement aussi silencieusement pour n'importe quel vrai client. Personne ne l'avait remarqué puisque rien ne bloque le visiteur.

**Correctif définitif (en cours, nécessite l'utilisateur)** : vérifier un sous-domaine d'envoi dans Resend (ex. `mail.osmm-mtl.site`), ajouter les enregistrements DNS générés par Resend chez le registrar du domaine (pas accessible par Claude), puis configurer `MAILER_FROM_EMAIL` sur `gravity-mailer` une fois le domaine vérifié.

**Correctif immédiat déployé (13 septembre 2026)** : ajout d'un canal FormSubmit (même pattern que Coaching/Pickup/OSMM) dans `gravity-basketball-mtl/script.js`, vers `Gavitybasketball@gmail.com`, pour Ligue 3v3 / Ligue Maison / U15 Masculin uniquement — **pas pour Gravity Prep**, qui garde sa notification dédiée existante (`basketball-mtl-prep-admin`) pour éviter un doublon une fois Resend réparé.

## Suspension de sécurité Resend (13 septembre 2026, état actuel)

En poursuivant la vérification du domaine `mail.osmm-mtl.site` sur Resend (PR #41), une anomalie a été détectée : les enregistrements SPF affichés par Resend pour ce domaine — **et pour un domaine de test flambant neuf, sans lien avec ce projet** — pointaient vers `forge.rmta.net`, l'infrastructure d'un service tiers appelé **« SendBeam »** (`sendbeam.io`), au lieu de l'infrastructure Resend habituelle (`amazonses.com`, confirmé par la documentation officielle Resend). SendBeam est un service réel, pas un logiciel malveillant connu, mais il n'a **aucun lien légitime avec Resend** — sa présence dans les enregistrements DNS suggérés par Resend est inexpliquée (hypothèses non tranchées : extension de navigateur altérant l'affichage de la page Resend, compte Resend compromis, ou autre anomalie côté compte).

**Mesure de précaution appliquée (PR #42, mergée)** : `RESEND_SUSPENDED = true` en tête de `gravity-mailer/netlify/functions/send-confirmation.js` — court-circuite toute requête avant l'appel à `api.resend.com`, retourne un 503 explicite. **Aucun appel à l'API Resend n'est effectué tant que ce flag est actif.** Ne repasser à `false` qu'une fois l'anomalie éclaircie et confirmée réglée par l'utilisateur.

**Conséquence couverte (PR #43, mergée)** : Gravity Prep a maintenant lui aussi un filet FormSubmit (`Gavitybasketball@gmail.com`), en plus de sa notification Resend existante (actuellement muette à cause de la suspension) — il n'y a donc plus de programme sans notification admin pendant la suspension. Doublon assumé une fois Resend réactivé.

**Reste à faire côté utilisateur si on veut un jour élucider l'anomalie Resend** (non bloquant, Resend est abandonné — voir section suivante) :
1. Vérifier la sécurité du compte Resend (mot de passe, connexions récentes, clés API) — envisager de régénérer `RESEND_API_KEY`.
2. Revérifier la page de vérification de domaine Resend depuis un appareil/navigateur de confiance (sans extensions), idéalement en navigation privée, pour confirmer si les valeurs `forge.rmta.net` réapparaissent.
3. Vérifier dans la zone DNS Netlify (`osmm-mtl.site`) qu'aucun enregistrement pointant vers `rmta.net` n'a été ajouté par erreur — supprimer si c'est le cas.
4. Contacter le support Resend si l'anomalie persiste.

## Migration Resend → Brevo (13 septembre 2026)

Plutôt que d'attendre l'élucidation de l'anomalie Resend ci-dessus, l'utilisateur a choisi d'**abandonner Resend et de passer à Brevo** (ex-Sendinblue) pour l'envoi de tous les courriels transactionnels. `RESEND_SUSPENDED` est retiré (devenu inutile, Resend n'est plus appelé nulle part).

**Trois fonctions Netlify migrées** (toutes appelaient directement `api.resend.com`, remplacé par `api.brevo.com/v3/smtp/email`) :
- `gravity-mailer/netlify/functions/send-confirmation.js` — confirmations clients + notification admin Gravity Prep.
- `gravity-admin-dashboard/netlify/functions/notify-espace-joueurs.js` — alertes courriel Espace Joueurs.
- `gravity-admin-dashboard/netlify/functions/send-campaign.js` — envoi de campagnes depuis le Dashboard.

**Différences d'API à retenir** (si une nouvelle fonction envoie un courriel un jour) :
- Header d'authentification : `api-key: <clé>` (pas `Authorization: Bearer`).
- Champ expéditeur : objet `sender: { name, email }` (pas une chaîne `"Nom <adresse>"`).
- Destinataires : `to` / `bcc` sont des tableaux d'objets `{ email }` (pas des chaînes).
- Corps HTML : champ `htmlContent` (pas `html`).
- **Pas de domaine de test** : contrairement à Resend (`onboarding@resend.dev`), Brevo n'autorise aucun envoi sans expéditeur vérifié au préalable (soit une adresse simple confirmée par courriel, soit un domaine complet vérifié par DNS) — sans ça, l'API rejette la requête (pas d'envoi silencieusement dégradé comme avec le domaine de test Resend).

**Variables d'environnement Netlify à configurer par l'utilisateur** (sur les sites `gravity-mailer` ET `gravity-admin-dashboard`, chacun a ses propres variables d'environnement) :
- **`BREVO_API_KEY`** — Brevo → icône profil → SMTP & API → onglet Clés API → générer une nouvelle clé.
- **`MAILER_FROM_EMAIL`** (déjà existante pour `gravity-mailer` depuis l'époque Resend, réutilisée telle quelle) — doit être un expéditeur **vérifié dans Brevo**. Deux options : (1) expéditeur simple (rapide : ajouter l'adresse dans Brevo → Expéditeurs, Domaines & IP dédiées → cliquer le lien de confirmation reçu par courriel → envoi possible vers n'importe quel destinataire, aucun DNS à toucher) ou (2) domaine complet vérifié par DNS (`mail.osmm-mtl.site`, meilleure délivrabilité à terme, même démarche que Resend en son temps).

Tant que `BREVO_API_KEY` ou `MAILER_FROM_EMAIL` (adresse vérifiée) manque, les trois fonctions renvoient une erreur 500 explicite plutôt que d'échouer silencieusement.

## Billet Zeffy Gravity Prep + création automatique de l'accès Espace Joueurs (13 septembre 2026)

Contexte tiré des documents fournis par l'utilisateur (contrat joueur Post-Grad, description de saison, présentation du Circuit Prep U) : Gravity Prep = le programme "Post-Grad" (saison du 1er octobre 2026 au 28 mars 2027, 850 $, payable en un seul versement sur Zeffy — le contrat prévoit un échéancier en 3 versements mais l'utilisateur a choisi un billet Zeffy unique plein tarif plutôt que 3 billets par versement).

**Ce qui a été fait dans ce repo :**
- `gravity-basketball-mtl/documents/contrat-joueur-postgrad-2026-2027.pdf` : le contrat joueur, hébergé publiquement pour pouvoir être lié depuis le billet Zeffy (case à cocher "j'ai lu et j'accepte" au moment du paiement — pas de vraie signature électronique, même logique que la case décharge déjà existante sur le formulaire d'inscription).
- `gravity-admin-dashboard/netlify/functions/zeffy-webhook-prep.js` : nouvelle fonction Netlify qui reçoit les paiements complétés Zeffy (webhook), et **crée directement l'accès Espace Joueurs du joueur dès son premier paiement**, sans attendre que l'admin clique "Créer un accès" dans le Dashboard :
  - Cherche une fiche joueur existante (`players`, `site = 'gravity-basketball'`, `age_category = 'Prep'`) dont le courriel correspond à celui du paiement.
  - Si aucune fiche n'existe encore, en crée une minimale (nom + courriel seulement, tirés du paiement Zeffy — `program: 'equipe'`, `age_category: 'Prep'`) ; l'admin complète ensuite équipe/numéro/photo dans "Mes équipes — Joueurs" comme d'habitude, ça ne bloque pas l'accès du joueur.
  - Crée le compte Supabase Auth + envoie le courriel d'accès (même gabarit `espace-joueurs-access` que la création manuelle) + alerte Gavitybasketball@gmail.com (filet FormSubmit) pour signaler qu'une fiche a été créée automatiquement et reste à compléter.
  - Idempotent : si la fiche a déjà un `auth_user_id`, ne fait rien (évite les doublons sur un retry du webhook ou un paiement répété).
  - **Le format exact du payload envoyé par Zeffy n'a pas pu être vérifié** (accès à `support.zeffy.com` bloqué depuis cet environnement) — l'extraction du courriel/nom fouille le JSON reçu plutôt que de viser des chemins fixes, et un filtre sur le mot "prep" dans le payload ignore les paiements des autres programmes si jamais le webhook Zeffy est réglé au niveau du compte plutôt que par événement. Si un vrai paiement de test ne déclenche pas l'invitation, les logs Netlify de cette fonction affichent le payload brut reçu — à consulter en premier pour ajuster l'extraction.

**Billet créé le 14 septembre 2026** : `https://www.zeffy.com/en-CA/ticketing/gravity-prep-saison-2026--2027`, branché dans `ZEFFY_LINKS['Gravity Prep']` (`gravity-basketball-mtl/script.js`) — un joueur qui choisit "Zeffy" comme mode de paiement pour Gravity Prep est maintenant redirigé vers ce billet au lieu du message "paiement bientôt disponible".

**Reste à faire côté utilisateur :**

2. Dans Zeffy → Settings → Notifications (sur ce billet) : activer une notification par courriel vers `Gavitybasketball@gmail.com`, comme pour Talent Perlé.
3. Dans Zeffy → Settings → Integrations → Webhooks : ajouter un webhook pointant vers `https://gravity-admin-dashboard.netlify.app/.netlify/functions/zeffy-webhook-prep?key=<secret>`.
4. Sur Netlify, site `gravity-admin-dashboard` → variables d'environnement : ajouter **`ZEFFY_PREP_WEBHOOK_SECRET`** (choisir une valeur, la mettre aussi dans l'URL du webhook Zeffy ci-dessus) — `SUPABASE_SERVICE_ROLE_KEY` est déjà requise pour `create-player-account.js`, réutilisée ici.
5. Une fois le billet créé, donner l'URL Zeffy (`zeffy.com/en-CA/ticketing/...`) pour qu'elle soit ajoutée à `ZEFFY_LINKS['Gravity Prep']` dans `gravity-basketball-mtl/script.js` (actuellement absent — un joueur qui choisit "Zeffy" comme mode de paiement pour Gravity Prep voit un message "paiement bientôt disponible").
6. Faire un vrai paiement de test une fois tout branché, et transmettre le contenu des logs Netlify de `zeffy-webhook-prep` si l'invitation ne part pas automatiquement.

## Intégration API Meta / Instagram (23 septembre 2026)

Compte branché : **@gravitybasketball_mtl** (compte Instagram professionnel déjà relié à une Page Facebook, confirmé par l'utilisateur). Les 4 usages demandés ont été construits :

- **Fil automatique sur le site** : la section "Vidéos" de `gravity-basketball-mtl` affiche d'abord les 12 derniers reels/vidéos du compte (lus via l'API), avec repli sur la liste manuelle `instagram_carousel` si l'API est indisponible ou pas encore configurée. Le repli affiche maintenant aussi les vidéos téléversées (`video_url`), pas seulement les liens (`post_url`).
- **Dashboard → nouveau groupe de menu "Instagram"** (visible seulement pour les admins qui gèrent `gravity-basketball`, chargé seulement à l'ouverture) : statistiques (abonnés, portée/interactions/visites du profil sur 28 jours, stats par publication), publication de photo/reel, commentaires (répondre, masquer), messages privés (lire, répondre).
- **Bouton "Publier sur Instagram"** sur chaque joueur de "Mes équipes — Joueurs" : génère la fiche joueur en JPEG et pré-remplit le formulaire de publication (rien n'est publié sans clic de confirmation).

**Architecture** : une seule fonction Netlify `gravity-admin-dashboard/netlify/functions/instagram.js` (`?action=...`). Le jeton Meta ne quitte jamais le serveur. `action=feed` est public (mis en cache 15 min sur le CDN Netlify) ; toutes les autres actions exigent le jeton Supabase d'un admin qui gère `gravity-basketball` (même vérification que `create-player-account.js`). La publication se fait en 3 appels (conteneur → attente du traitement → publication) parce qu'un reel peut dépasser la durée max d'une fonction Netlify. Les fichiers à publier transitent par le bucket public `gravity-media/instagram/` (Meta doit pouvoir les télécharger par URL publique ; photos converties en JPEG côté navigateur, seul format accepté).

**Limites Meta à connaître** : réponse aux DM seulement dans les 24 h suivant le dernier message de la personne ; 50 publications max par 24 h via l'API ; certaines statistiques par publication ne sont pas disponibles pour tous les types (affichées "—").

**Reste à faire côté utilisateur (sinon le Dashboard affiche "META_PAGE_ACCESS_TOKEN manquant" et le site reste sur la liste manuelle)** :
1. Créer une app sur developers.facebook.com (type "Business"), y ajouter le produit "Instagram" (configuration avec connexion Facebook).
2. Dans Graph API Explorer, choisir l'app, générer un jeton utilisateur avec les permissions `instagram_basic`, `instagram_content_publish`, `instagram_manage_comments`, `instagram_manage_insights`, `instagram_manage_messages`, `pages_show_list`, `pages_read_engagement`, `pages_manage_metadata`, `pages_manage_posts` (publication de vidéos sur la Page depuis Art craft, ajoutée le 20 octobre 2026), `business_management`.
3. Le prolonger dans l'Access Token Debugger ("Extend Access Token") → jeton utilisateur longue durée.
4. Dans Graph API Explorer avec ce jeton longue durée : `GET me/accounts` → copier l'`access_token` de la Page Gravity (jeton de Page qui n'expire pas).
5. Netlify, site `gravity-admin-dashboard` → variables d'environnement : **`META_PAGE_ACCESS_TOKEN`** = ce jeton de Page. (Optionnel : `META_IG_USER_ID`, sinon déduit automatiquement.)
6. Pour les messages privés : dans l'app Instagram → Paramètres → Messages et appels → Outils connectés → activer "Autoriser l'accès aux messages".
L'app peut rester en mode développement tant que seuls des comptes ayant un rôle sur l'app (l'utilisateur) s'en servent — pas besoin de revue d'app Meta.
